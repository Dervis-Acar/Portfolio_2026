Cairn

One stone at a time.

An installable progressive web app that runs a whole day: tasks, calendar, focus sessions, nutrition, body composition, work hours, reading notes and startup idea validation. It is self hosted, in production, and used daily.

The part worth looking at is the voice assistant. You hold a button, say a sentence in Dutch or English, and it becomes real rows in Postgres. Getting that right was far less about calling a model than about the validation boundary around it.

ENGINEERING DECISIONS WORTH A LOOK
rule_settings

The validation boundary

Ten tools, each with a Zod input schema. Enums and units are re-normalised in application code afterwards, because a model that returns a plausible but invalid meal type should never be able to corrupt a row.

search_check

Deterministic beats generative

A tiered scoring matcher resolves a spoken food name to a real database row before the model's calorie guess is used. A 157 entry Dutch to English synonym table runs first, because as a fallback it matched dish names instead of ingredients.

shield_lock

Four layers, then RLS

A proxy redirect, an authoritative check in the layout, a re-check inside every server action, and Row Level Security in Postgres. The first three can all have bugs and still not leak another user's rows.

translate

Bilingual at every layer

Dutch lives in the transcription prompt, the synonym table, the unit parser (pond, ons, and "1,5 kg" written with a comma) and the enum normaliser. It is a first class input language, not a translation pass.

notifications_paused

Reminders that check first

The dispatcher reads your data before sending, so a day you already logged produces nothing. Times are stored as local wall clock plus timezone, so 19:00 stays 19:00 through daylight saving and travel.

dashboard_customize

A typed widget registry

Each of the 12 dashboard widgets declares its data needs once. The fetcher de-duplicates them across whatever is on screen and resolves them in a single batch, and the widget's data type is derived from that map. Adding a widget is two lines with no new queries.

Performance was measured, not guessed

The biggest win was invisible to route level analysis and only turned up through bundle inspection.

01 // 552 KB OF SESSION REPLAY

Sentry Session Replay was loading in the root layout, so it shipped on every page and recorded DOM mutations during scroll. Removing it and cutting trace sampling to 10% in production took that weight off the whole app.

02 // 12 AUTH ROUND TRIPS PER RENDER

The auth helper was called 12 times in a single render pass, each one a Supabase round trip of about 65 ms. Wrapping it in React cache collapsed all 12 into one.

03 // AN AUTH CHECK ON EVERY PREFETCHED LINK

The bottom navigation puts every route in the viewport at once, and Next.js prefetches all of them, so each page view triggered a round trip per link. The proxy now skips the check for prefetches, deliberately scoped to exclude API routes, because that header is client supplied and honouring it on the voice endpoint would let an anonymous caller spend AI credits.

04 // CHARTS THAT FROZE AT ZERO

Recharts animates on mount with requestAnimationFrame. On a backgrounded tab or a low power device that gets throttled, so bars stayed at zero height and the chart looked broken. Reproduced with a plain Recharts control case, then fixed by turning mount animation off.

05 // ONE OPTIMISATION LEFT UNDONE

The backdrop blur on the fixed navigation bars is a plausible GPU cost, but frame timing could not be measured in the available environment. Changing it would have been a guess dressed up as an optimisation, so it was left alone and recorded as such.

ON THE ENCRYPTION CLAIM

Saying exactly what it does and does not protect

Progress photos are encrypted in the browser with AES-256-GCM before upload, so the server only ever stores ciphertext. That protects against a stolen backup or a leaked volume.

It is not zero knowledge, and the code says so. The key is derived from the account id, which is not a secret, so the server operator could derive it. Claiming otherwise would be the easy thing to write and the wrong thing to ship.

Because of that, access control is enforced separately. Every read is confined to the caller's own directory using a resolved path check rather than string comparison, and anything outside it returns 404 instead of 403, so the endpoint never confirms whether another user's file exists. Verified against a 17 case traversal suite.
